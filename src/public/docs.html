Dlp Wrapper

A self-hosted REST API wrapping yt-dlp. Fetch metadata, resolve direct CDN URLs, or download MP4/MP3 from 1,750+ sites — drop it into a web app or a Discord bot over plain HTTP.

$ curl -H "x-api-key: $KEY" "$BASE/api/media/info?url=..."

Quick start

Every request goes through the base URL of wherever you've deployed this — locally that's http://localhost:8080, on Render it's the onrender.com URL your service gets.

# local
npm install
npm start
# → listening on http://localhost:8080

Every endpoint lives under /api. All routes below are relative to that.

Authentication

Set the API_KEY environment variable and every request must include it as a header:

x-api-key: your-secret-key
Left unset, the API is fully open. That's fine for poking at it locally, but set API_KEY before pointing a public URL at it. The key is checked with a constant-time comparison, and applies to every /media/* route — /healthz is always open.

GET /api/healthz

Liveness check. No auth required. Returns:

{ "status": "ok" }

GET /api/capabilities

What this particular install can actually do. Most “site X doesn't work” reports come down to the environment rather than the extractor — no ffmpeg, no cookies, no TLS impersonation — so check here first.

{
  "ytdlpVersion": "2025.09.26",
  "ffmpeg": true,
  "ffprobe": true,
  "impersonation": false,
  "impersonateTarget": null,
  "cookieDomains": ["youtube.com", "instagram.com"],
  "notes": []
}

GET /api/media/info

Full metadata for any yt-dlp-supported URL — title, thumbnail, duration, uploader, live status, subtitle languages, and every available format. The response shape is identical whether the source is a video site, an audio host, or an image post, so clients need no per-site branching.

ParamRequiredDefaultDescription
urlrequired—Source URL. Public http/https only; a bare host like youtu.be/abc is accepted and upgraded to https.
playlistoptionalfalseReturn every entry of a playlist/album/channel/multi-clip post instead of just the first.
limitoptional50Max entries when playlist=true.
itemoptional—1-based index of a single item inside a playlist/post.
curl -H "x-api-key: $KEY" \
  "$BASE/api/media/info?url=https://www.youtube.com/watch?v=dQw4w9WgXcQ"
{

  "id": "dQw4w9WgXcQ",
  "title": "...",
  "thumbnail": "https://...",      // largest available, even when the extractor only fills `thumbnails`
  "durationSeconds": 212,
  "uploader": "...",               // uploader / channel / creator / artist, whichever the site provides
  "webpageUrl": "https://...",
  "extractor": "youtube",
  "uploadDate": "2009-10-25",
  "isLive": false,
  "liveStatus": "not_live",
  "hasVideo": true,
  "hasAudio": true,
  "isPlaylist": false,
  "subtitleLanguages": ["en"],
  "formats": [
    { "formatId": "22", "ext": "mp4", "resolution": "1280x720", "width": 1280, "height": 720,
      "fps": 30, "protocol": "https", "filesizeApprox": 34521098, "tbr": 1500,
      "vcodec": "avc1.64001F", "acodec": "mp4a.40.2",
      "hasVideo": true, "hasAudio": true, "isManifest": false, "isDrm": false }
  ]
}
Sites that bundle several clips into one post (X/Twitter threads, Reddit galleries, TikTok photo carousels, Instagram multi-item posts) come back as the first playable item plus a partOfPlaylist summary. Pass playlist=true for the full list, then fetch a specific one with item=N. Storyboard/preview-grid formats are filtered out of formats.

GET /api/media/direct-url

Resolves the underlying CDN URL(s) without routing any bytes through this server. Good for Discord embeds or an HTML5 <video src>.

ParamRequiredDefaultDescription
urlrequired—Source URL
formatoptionalb/bv*+ba/ba/bv*yt-dlp format selector. The default prefers a single playable file and falls back through merge pairs, audio-only, then video-only, so it resolves on every kind of source. A selector the site can't satisfy is retried loosened instead of failing.
itemoptional—1-based index inside a multi-item post
curl -H "x-api-key: $KEY" \
  "$BASE/api/media/direct-url?url=https://vimeo.com/76979871"
{
  "title": "...",
  "extractor": "vimeo",
  "isLive": false,
  "urls": ["https://cdn.example.com/..."],
  "streams": [
    { "url": "https://cdn.example.com/...", "formatId": "http-1080p", "ext": "mp4",
      "protocol": "https", "resolution": "1920x1080", "hasVideo": true, "hasAudio": true,
      "isManifest": false,
      "headers": { "User-Agent": "...", "Referer": "https://vimeo.com/" } }
  ],
  "requiresMerge": false,
  "expiresAt": "2025-01-01T12:00:00.000Z"
}
Replay the headers. Instagram, TikTok, Facebook, Bilibili and friends 403 a direct URL fetched without the original Referer/User-Agent. When isManifest is true the URL is an HLS/DASH manifest and needs a player (hls.js, ffmpeg, VLC) rather than a plain GET; when requiresMerge is true video and audio are separate streams. In both cases /media/download does the work for you.

GET /api/media/download

Downloads via yt-dlp into a temp directory, then streams the file back as an attachment.

ParamRequiredDefaultDescription
urlrequired—Source URL
extoptionalmp4mp4, webm, mp3, m4a, opus, audio (best audio, no re-encode) or auto (source container, no conversion — fastest and works everywhere)
formatoptionalper-ext selectoryt-dlp format selector, overriding the default for that ext
itemoptional—1-based index inside a multi-item post
allowLiveoptionalfalseAllow recording a live stream. Off by default because a live download only ends at YTDLP_DOWNLOAD_TIMEOUT_MS.
curl -H "x-api-key: $KEY" -OJ \
  "$BASE/api/media/download?url=https://vimeo.com/76979871&ext=mp3"
ext is best-effort, not a transcode promise. A webm/opus-only source asked for as mp4 is remuxed when the codecs allow it and otherwise comes back in its original container — Content-Type and the filename always describe what's actually in the body, so check them rather than assuming. If the requested format doesn't exist on that site the request is retried with a looser selector instead of failing, and if a remux fails it's retried keeping the source container.

Filenames are sent RFC 6266-encoded, so non-ASCII titles survive intact:

Content-Disposition: attachment; filename="_____ _____.mp4"; filename*=UTF-8''%D0%9F%D1%80%D0%B8%D0%BC%D0%B5%D1%80.mp4

This endpoint has its own stricter rate limit and concurrency cap (see below) since each request spins up a real ffmpeg/yt-dlp process. Disconnecting mid-download kills the subprocess.

GET /api/media/extractors

The list of sites this yt-dlp build supports, read straight from the binary — useful for checking a source before wiring it up.

ParamRequiredDefaultDescription
queryoptional—Case-insensitive substring filter
limitoptional100Max names returned
curl -H "x-api-key: $KEY" "$BASE/api/media/extractors?query=tiktok"
{ "total": 1750, "matched": 8, "query": "tiktok",
  "extractors": ["TikTok", "tiktok:collection", "tiktok:live", "tiktok:user", "vm.tiktok"] }

Working with every site

yt-dlp supports 1,750+ sites and they behave nothing alike. The API smooths over most of that for you:

  • Any media type — video, audio-only hosts (SoundCloud, Bandcamp, podcasts) and image posts all return the same shape, tagged with kind.
  • Any format layout — progressive-only, split video+audio, HLS/DASH manifests, or extractors that expose a single bare URL and no format list at all.
  • Multi-item posts — collapsed to the first item by default, fully listable with playlist=true.
  • Fallback selectors — every default format selector degrades through muxed → merge → audio-only → video-only, and unsatisfiable selectors are retried loosened.
  • Classified failures — a login wall, a geo-block and a dead link are three different status codes, not one generic 422.

Three environment knobs cover the sites that still push back:

ProblemFix
Login walls, age gates, “confirm you're not a bot” (YouTube from a cloud IP, Instagram, X)YTDLP_COOKIES_DIR with a per-site jar — see cookies
TLS-fingerprint blocking / blanket 403sYTDLP_IMPERSONATE=chrome (needs yt-dlp[curl-cffi]; the bundled Dockerfile installs it)
Geo-restrictions, datacentre IP bansYTDLP_PROXY, or YTDLP_GEO_BYPASS_COUNTRY

Site-specific tuning (e.g. YouTube player clients) goes through YTDLP_EXTRACTOR_ARGS, newline- or |-separated:

YTDLP_EXTRACTOR_ARGS="youtube:player_client=android,web|generic:impersonate"

Error codes

Every failure returns JSON with a stable code, a human error message, usually an actionable hint, and the cleaned-up yt-dlp output in detail:

{

  "code": "auth_required",
  "hint": "Export cookies from a logged-in browser and set YTDLP_COOKIES_FILE (or drop a <domain>.txt into YTDLP_COOKIES_DIR).",
  "detail": "[instagram] 123: Requested content is not available, rate-limit reached or login required"
}

Rate limits & concurrency

Two layers protect the container from being overwhelmed: a request-rate limit per client IP, and a hard cap on concurrent yt-dlp/ffmpeg processes.

Env varDefaultApplies to
RATE_LIMIT_MAX / RATE_LIMIT_WINDOW_MS30 / 60000Whole API, per client IP
DOWNLOAD_RATE_LIMIT_MAX / DOWNLOAD_RATE_LIMIT_WINDOW_MS10 / 600000/media/download only
DLP_MAX_CONCURRENT_INFO8Concurrent /media/info + /media/direct-url
DLP_MAX_CONCURRENT_DOWNLOADS2Concurrent /media/download

By default, hitting the concurrency cap returns an immediate 429. Set QUEUE_ENABLED=true to wait for a free slot instead:

Env varDefaultDescription
QUEUE_ENABLEDfalseQueue instead of rejecting immediately
QUEUE_MAX_WAIT_MS15000Give up and return 429 after this long waiting
QUEUE_MAX_LENGTH50Reject immediately once this many requests are already waiting

Set REDIS_URL to back the rate limiter with Redis instead of in-memory counters — counts then survive restarts and are shared across multiple instances rather than reset-per-process.

Metadata caching

/media/info and /media/direct-url cache their responses, since the same url is often requested repeatedly (a Discord command run twice, a web app re-rendering). /media/download is never cached — it's a stream, not a storable value.

Env varDefaultNotes
CACHE_TTL_INFO_MS3000005 minutes
CACHE_TTL_DIRECT_URL_MS120000Shorter — CDN URLs carry short-lived expiry tokens
CACHE_MAX_ITEMS500In-memory fallback only; ignored when REDIS_URL is set

Without REDIS_URL, the cache is an in-memory map scoped to this process. With it, entries are shared across every instance.

Per-IP quotas

A longer-window ceiling per IP, on top of the short-window rate limit above — e.g. "50 downloads per day" rather than "10 per 10 minutes". Opt-in, since not every self-hoster wants a hard daily cap.

Env varDefaultNotes
QUOTA_ENABLEDfalseMaster switch for all three quotas below
QUOTA_WINDOW_MS8640000024 hours
QUOTA_MAX_INFO500Per IP, per window
QUOTA_MAX_DIRECT_URL500Per IP, per window
QUOTA_MAX_DOWNLOADS50Per IP, per window

An IP over quota gets 429 with a Retry-After header. Counts use REDIS_URL when set, otherwise an in-memory map.

Metrics

Prometheus-format metrics are served at GET /metrics: request counts and latency per route, active job gauges, cache hit/miss counts, and quota rejections — plus the usual process/CPU/memory metrics.

curl http://localhost:8080/metrics

Set METRICS_KEY to require an x-metrics-key header on scrape requests. Left unset, /metrics is open — fine if you're only scraping it over a private network.

Security notes

  • SSRF guard — every url is checked before it reaches yt-dlp: must be http/https, and must resolve to a public address (blocks loopback, private ranges, and cloud metadata endpoints).
  • Constant-time key check — API_KEY comparison doesn't leak timing information.
  • CORS is closed by default — no browser origin can call the API until you set ALLOWED_ORIGINS.
  • Temp files are swept — per-request download directories are cleaned up on completion, with a periodic sweep for anything left behind by a crash.
If a web app calls this API, don't ship API_KEY to client-side JS — proxy the request through your own backend instead. Anything sent to a browser is extractable.

Cookies & logins

Login walls are the single most common reason a source fails: YouTube demands a browser session from any cloud IP, and Instagram, X, Facebook, Bilibili, niche forums and most paywalled sites want an account. That's a yt-dlp/site reality, not an API limitation — the fix is always the same: give it cookies from a real logged-in browser.

One site — export cookies in Netscape format (e.g. the “Get cookies.txt LOCALLY” extension), mount the file, and point at it:

YTDLP_COOKIES_FILE=/secrets/cookies.txt

Several sites — a single jar shared across sites is useless at best and account-flagging at worst, so use a directory of per-site jars named after the domain they belong to:

/secrets/cookies/
  youtube.com.txt
  instagram.com.txt
  x.com.txt

YTDLP_COOKIES_DIR=/secrets/cookies

The jar whose domain is the longest suffix match for the request host wins (youtube.com.txt also covers m.youtube.com), falling back to YTDLP_COOKIES_FILE if one is set. GET /api/capabilities lists the domains currently loaded.

From there, cookie handling is managed automatically:

  • Writable working copy — each jar is copied to a writable temp path at startup. yt-dlp rewrites its cookie jar after every run as tokens rotate, which silently fails against a read-only mount (e.g. Render Secret Files) — working from a copy keeps that refresh working.
  • Re-sync on change — sources are re-checked on an interval (COOKIE_SYNC_INTERVAL_MS, default 5 minutes); dropping in a freshly exported file picks it up without a restart, and new <domain>.txt files are picked up too.
  • Expiry warnings — expiry timestamps are parsed per jar and logged as a warning when entries are expired or expiring within COOKIE_EXPIRY_WARNING_MS (default 24h), so you know which site to re-export.

Those sessions are shared by every caller of the API — treat them accordingly. None of this logs into anything on your behalf; you still export cookies from a real logged-in browser yourself.

curl

BASE="https://your-app.onrender.com/api"
KEY="your-secret-key"

# metadata from any supported site
curl -H "x-api-key: $KEY" "$BASE/media/info?url=https://vimeo.com/76979871"
curl -H "x-api-key: $KEY" "$BASE/media/info?url=https://soundcloud.com/forss/flickermood"
# every clip in a multi-item post
curl -H "x-api-key: $KEY" "$BASE/media/info?url=https://x.com/user/status/123&playlist=true"
# CDN URL + the headers its CDN expects
curl -H "x-api-key: $KEY" "$BASE/media/direct-url?url=https://vimeo.com/76979871"
# download: mp4, audio-as-mp3, or untouched source container
curl -H "x-api-key: $KEY" -OJ "$BASE/media/download?url=https://vimeo.com/76979871&ext=mp4"
curl -H "x-api-key: $KEY" -OJ "$BASE/media/download?url=https://soundcloud.com/forss/flickermood&ext=mp3"
curl -H "x-api-key: $KEY" -OJ "$BASE/media/download?url=https://www.tiktok.com/@u/video/123&ext=auto"
# is a site supported?
curl -H "x-api-key: $KEY" "$BASE/media/extractors?query=bilibili"

Web app (fetch)

Call this from your own backend, not directly from the browser, so the API key never reaches client-side JS:

const res = await fetch(`${BASE}/media/info?url=${encodeURIComponent(url)}`, {
  headers: { "x-api-key": process.env.DLP_WRAPPER_KEY },
});
const info = await res.json();

Discord bot

A minimal discord.js example ships in examples/discord-bot. The core call looks like:

const r = await fetch(`${DLP_WRAPPER_BASE}/media/direct-url?url=${encodeURIComponent(url)}&format=best`, {
  headers: { "x-api-key": DLP_WRAPPER_KEY },
});
const { urls } = await r.json();
await message.reply(`Direct link: ${urls[0]}`);

Deploy — Render

The repo includes a render.yaml blueprint.

  1. Push this repo to GitHub
  2. On Render: New → Blueprint, connect the repo
  3. Render reads render.yaml and provisions the service — it generates API_KEY for you
  4. Set ALLOWED_ORIGINS to your web app's origin if it'll call the API from browser JS
  5. Deploy — your base URL is https://<service-name>.onrender.com/api
The default plan in render.yaml is sized for light use. Bump it if you expect concurrent transcodes — ffmpeg and yt-dlp are both CPU/RAM heavy.

Deploy — Docker

docker build -t dlp-wrapper .
docker run --rm -p 8080:8080 \
  -e PORT=8080 \
  -e API_KEY=your-secret-key \
  dlp-wrapper
